## 0. v0.1 Scope

This document covers v0.1 only. Do not implement anything outside this scope.

**In scope for v0.1:**

- Core package: token validation, PAT system, scope matcher, framework-agnostic handlers, bypass mode, audit callbacks
- One token store: `memoryTokenStore` (in-process; for tests and local dev)
- One web adapter: Express
- One example: `hello-world` (minimal protected HTTP server with PAT issuance)
- Unit + integration + security tests for the core
- One doc: a quickstart that gets a developer to a running protected server

**Deferred to v0.2+ (do not start, do not stub):**

- Hono adapter

- Config file format (`mcp-authkit.config.ts`)

- Dynamic Client Registration (RFC 7591)
- JWT Bearer Assertion grant (RFC 7523)
- Client Credentials grant (RFC 6749 §4.4)

- Postgres, filesystem, stdio examples
- Production stdio support
- Token-exchange and on-behalf-of flows

Build v0.1 well. Resist the urge to scaffold v0.2.

## 1. Mission

Three problems server authors currently get wrong:

1. **Spec-compliant OAuth 2.1 for MCP servers.** Most MCP servers either skip auth or implement partial OAuth that fails real review.
2. **Programmatic access without friction.** OAuth authorization code + PKCE is hostile to scripts. Builders writing Python/Node scripts must either copy refresh tokens by hand or skip auth.
3. **Per-tool, per-operation authorization.** MCP stops at "is this caller authenticated." Real systems need "this caller can SELECT from analytics tables but not UPDATE them."

Success: a developer stands up a secure MCP server in under a day; a Python script consuming it doesn't dread the auth.

## 2. Hard Constraints (Locked Decisions)

- **Name:** `mcp-authkit`
- **Foundation:** built on `@modelcontextprotocol/sdk`. Wrap and extend; don't reimplement.
- **MCP spec version:** **2025-06-18 (Streamable HTTP).** Use this version everywhere; do not chase later drafts.
- **Primary transport:** HTTP (Streamable HTTP).
- **Secondary transport:** stdio, local-dev only via bypass mode (section 11).
- **Web framework:** framework-agnostic core. Express adapter ships in v0.1 as a separate entry point. Core has zero Express imports.
- **Logger:** pino. Logger instance is injectable; framework does not abstract over arbitrary loggers.
- **UI:** headless only. PAT REST endpoints; consumers build their own UI.
- **Authorization server mode:** Mode A only (proxy/validate tokens from an external AS like Auth0, Keycloak, WorkOS, Cognito). Running your own AS is deferred.
- **JWT library:** `jose`.
- **Monorepo tool:** pnpm workspaces.
- **CLI framework (when v0.2 happens):** `commander`.
- **Audit callbacks:** included in v0.1 (see section 12).

## 3. Background

MCP servers per the 2025-06-18 spec are OAuth 2.1 Resource Servers. They issue 401 challenges with `WWW-Authenticate` headers pointing to Protected Resource Metadata, which points to an Authorization Server. The AS handles consent and token issuance. The MCP server validates incoming bearer tokens.

Token boundaries are strict: an MCP server must never accept an upstream third-party token (e.g., a GitHub access token) as if it were an MCP token, and must never forward MCP tokens to upstream APIs. RFC 8707 Resource Indicators bind tokens to a specific audience to prevent token confusion.

Programmatic consumers don't have a browser. The standard answer is Device Authorization Grant (RFC 8628) + Personal Access Tokens (GitHub model). PATs are first-class in v0.1; the device grant is consumed from the external AS.

## 4. Standards Compliance

The implementation MUST comply with:

- MCP Authorization specification, **2025-06-18** revision
- OAuth 2.1 (draft-ietf-oauth-v2-1)
- RFC 9728 — OAuth 2.0 Protected Resource Metadata (`/.well-known/oauth-protected-resource`)
- RFC 8414 — OAuth 2.0 Authorization Server Metadata. **Used to discover the AS's JWKS URI and (if applicable) introspection endpoint from the issuer URL.** The framework consumes this metadata; it does not serve it.
- RFC 8707 — Resource Indicators. Every accepted token MUST have an `aud` equal to the server's resource indicator.
- RFC 7636 — PKCE.
- RFC 8628 — Device Authorization Grant.
- RFC 7662 — Token Introspection (when opaque tokens come from the AS).
- RFC 6750 — Bearer Token Usage.

Read each RFC before implementing the corresponding feature. Do not rely on summaries.

## 5. Architecture

Three layers, clearly separated:

**Transport.** Streamable HTTP via SDK transports. Stdio supported in bypass mode only. Host header validation on by default for HTTP (DNS rebinding mitigation).

**Auth.** Token validation middleware + PAT REST endpoints. Validation attaches an `AuthContext` to every request, identical shape regardless of token origin.

**Authorization.** Scope/capability matching, runs after auth, before tool execution. Gates tool calls.

Downstream tool handlers never need to know how the caller authenticated.

## 6. Public API and Types

### 6.1 Core types (this is the contract)

```typescript
import type { IncomingMessage, ServerResponse } from "node:http"
import type { Logger } from "pino"
import type { z } from "zod"
import type { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js"

export interface AuthContext {
  /** Stable user identifier from the token (sub claim, or PAT owner). */
  subject: string
  /** Token kind, useful for audit and conditional logic. */
  tokenType: "oauth" | "pat" | "bypass" | "static"
  /** Opaque token id; for OAuth this is jti, for PAT it's the store row id. */
  tokenId: string
  /** Effective scopes after PAT-vs-user intersection. Always normalized. */
  scopes: readonly string[]
  /** Token expiry; null only in bypass / static-token modes. */
  expiresAt: Date | null
  /** Raw claims for OAuth (jwt payload) or PAT metadata. */
  raw: Record<string, unknown>
}

export interface CreatePatInput {
  userIdentifier: string
  name: string
  scopes: readonly string[]
  expiresAt: Date
  /** SHA-256 of the token, computed by the framework. */
  tokenHash: Buffer
  /** Prefix + first/last chars for display; never the full token. */
  display: string
}

export interface StoredPat extends CreatePatInput {
  id: string
  createdAt: Date
  lastUsedAt: Date | null
  revokedAt: Date | null
}

export interface StoredPatPublic {
  id: string
  name: string
  scopes: readonly string[]
  display: string
  createdAt: Date
  expiresAt: Date
  lastUsedAt: Date | null
}

export interface CreateRefreshTokenInput {
  familyId: string
  tokenHash: Buffer
  subject: string
  scopes: readonly string[]
  expiresAt: Date
}

export interface StoredRefreshToken extends CreateRefreshTokenInput {
  id: string
  createdAt: Date
  rotatedAt: Date | null
}

export interface TokenStore {
  createPat(input: CreatePatInput): Promise<StoredPat>
  findPatByHash(hash: Buffer): Promise<StoredPat | null>
  listPatsByUser(userIdentifier: string): Promise<StoredPatPublic[]>
  revokePat(id: string, userIdentifier: string): Promise<void>
  rotatePat(
    id: string,
    userIdentifier: string,
    next: CreatePatInput,
  ): Promise<StoredPat>
  updatePatLastUsed(id: string, timestamp: Date): Promise<void>

  createRefreshToken(input: CreateRefreshTokenInput): Promise<void>
  findRefreshToken(hash: Buffer): Promise<StoredRefreshToken | null>
  rotateRefreshToken(
    oldHash: Buffer,
    next: CreateRefreshTokenInput,
  ): Promise<void>
  revokeRefreshTokenFamily(familyId: string): Promise<void>

  init?(): Promise<void>
  close?(): Promise<void>
}

export type ScopeMatcher = (
  required: string,
  held: readonly string[],
  ctx: { auth: AuthContext; input: unknown },
) => boolean | Promise<boolean>

export interface ScopeVocabularyEntry {
  /** Human description for UIs and docs. */
  description: string
  /** Optional parameter name. If present, the scope is a template:
   *  the effective scope is `<key>:<param-value>` at runtime. */
  resource?: string
  /** Other scope keys this one implies. Holder of this scope is treated
   *  as also holding the implied scopes. */
  implies?: readonly string[]
}

export type ScopeVocabulary = Record<string, ScopeVocabularyEntry>

export interface AuditEvent {
  type:
    | "pat.mint"
    | "pat.use"
    | "pat.revoke"
    | "pat.rotate"
    | "oauth.validate"
    | "oauth.reject"
    | "scope.allow"
    | "scope.deny"
  at: Date
  subject: string | null
  tokenId: string | null
  detail: Record<string, unknown>
}

export interface AuthKitConfig {
  /** RFC 8707 audience for tokens accepted by this server. */
  resourceIndicator: string

  auth: {
    authorizationServer: {
      issuer: string
      jwksUri: string
      /** Optional; used for RFC 7662 introspection of opaque AS tokens. */
      introspectionEndpoint?: string
      /** ms; default 3_600_000 (1h). */
      jwksCacheTtlMs?: number
    }
    tokenStore: TokenStore
    pat: {
      enabled: boolean
      /** Token prefix, e.g. "mcp_pat_". Required if enabled. */
      prefix?: string
      defaultExpiryDays?: number // default 90
      maxExpiryDays?: number     // default 365
      /** Grace period for rotated PATs, in seconds. Default 0. */
      rotationGraceSeconds?: number
    }
    bypass?: {
      enabled: boolean
      user: string
      scopes: readonly string[]
      /** Required to enable when NODE_ENV === "production". */
      allowInProduction?: boolean
    }
    /** Single env-var token for stdio / CI. Treated as a synthetic PAT. */
    staticToken?: {
      token: string
      user: string
      scopes: readonly string[]
    }
  }

  scopes: {
    vocabulary: ScopeVocabulary
    /** Custom matchers for rules the string system can't express. */
    customMatchers?: readonly ScopeMatcher[]
  }

  /** Returns the user's currently-granted scope set. Called on every PAT
   *  validation to compute the effective intersection. */
  resolveUserScopes: (userIdentifier: string) => Promise<readonly string[]>

  /** Optional pino instance; one is created if absent. */
  logger?: Logger

  /** Audit hooks. Awaited; throw to abort the triggering operation. */
  audit?: {
    onEvent?: (event: AuditEvent) => void | Promise<void>
  }
}

export interface RegisterToolOptions<I extends z.ZodRawShape> {
  name: string
  description: string
  inputSchema: I
  /** Either a static list or a function of the call. The function form is
   *  what makes per-input scope policy expressible. */
  requireScopes:
    | readonly string[]
    | ((args: {
        input: z.infer<z.ZodObject<I>>
        auth: AuthContext
      }) => readonly string[] | Promise<readonly string[]>)
  handler: (args: {
    input: z.infer<z.ZodObject<I>>
    auth: AuthContext
  }) => Promise<{ content: Array<{ type: "text"; text: string }> }>
}

export interface Handlers {
  /** Mount as the MCP request handler. */
  mcp: (req: IncomingMessage, res: ServerResponse) => Promise<void>
  /** RFC 9728 protected resource metadata. */
  metadata: (req: IncomingMessage, res: ServerResponse) => Promise<void>
  /** PAT REST endpoints. Routes: POST /, GET /, DELETE /:id, POST /:id/rotate. */
  pats: (req: IncomingMessage, res: ServerResponse) => Promise<void>
  /** Build a 401 challenge with the right WWW-Authenticate header. */
  challenge: (res: ServerResponse, reason?: string) => void
}

export interface AuthKit {
  registerTool<I extends z.ZodRawShape>(
    mcp: McpServer,
    options: RegisterToolOptions<I>,
  ): void
  handlers(mcp: McpServer): Handlers
}

export function createAuthKit(config: AuthKitConfig): AuthKit
```

### 6.2 Usage (hello-world target: under 50 lines)

```typescript
import { createAuthKit } from "mcp-authkit"
import { memoryTokenStore } from "mcp-authkit/stores/memory"
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js"
import express from "express"
import { z } from "zod"

const authkit = createAuthKit({
  resourceIndicator: "https://api.example.com/mcp",
  auth: {
    authorizationServer: {
      issuer: "https://auth.example.com",
      jwksUri: "https://auth.example.com/.well-known/jwks.json",
    },
    tokenStore: memoryTokenStore(),
    pat: { enabled: true, prefix: "mcp_pat_" },
  },
  scopes: {
    vocabulary: {
      "echo:say": { description: "Echo a string" },
    },
  },
  resolveUserScopes: async () => ["echo:say"],
})

const mcp = new McpServer({ name: "hello", version: "0.1.0" })

authkit.registerTool(mcp, {
  name: "echo",
  description: "Echo input",
  inputSchema: { text: z.string() },
  requireScopes: ["echo:say"],
  handler: async ({ input }) => ({
    content: [{ type: "text", text: input.text }],
  }),
})

const h = authkit.handlers(mcp)
const app = express()
app.use("/mcp", h.mcp)
app.use("/.well-known/oauth-protected-resource", h.metadata)
app.use("/pats", h.pats)
app.listen(3000)
```

## 7. Scope Vocabulary and Matching

Scopes are colon-delimited segments: `<namespace>:<operation>[:<resource>...]`.

### 7.1 Templates and parameters

A vocabulary entry with a `resource` field is a template. At runtime the consumer's `requireScopes` function returns the instantiated scope:

```typescript
scopes: {
  vocabulary: {
    "db:select": { description: "Read a table", resource: "table" },
    "db:update": { description: "Update a table", resource: "table" },
  },
}

// in a tool:
requireScopes: ({ input }) => {
  const tables = parseSqlTables(input.sql) // consumer's problem, see 7.4
  const op = parseSqlOperation(input.sql)
  return tables.map(t => `db:${op}:${t}`)
}
```

The matcher treats `db:select:analytics.events` as satisfied by any of: exact match, `db:select:analytics.*`, `db:select:*`, or `db:select:**`.

### 7.2 Wildcards

- `*` matches one segment
- `**` matches one or more segments
- Wildcards apply only at or after the resource position. The namespace and operation cannot be wildcarded.

### 7.3 Implications

`implies` declares that holding scope A also grants scope B for matching purposes:

```typescript
"db:write": {
  description: "Write access",
  resource: "table",
  implies: ["db:update", "db:delete"],
}
```

Implications are transitive and resolved at scope-set normalization time.

### 7.4 Domain parsing is the consumer's problem

The framework does not parse SQL, file paths, GraphQL queries, or any domain-specific input. Functions like `parseSqlTables` and `parseSqlOperation` are placeholders for code the consumer writes. The framework only matches scope strings.

### 7.5 Custom matchers

For policies the string system can't express (row-level, time-based, IP-based), register a `ScopeMatcher`. A required scope is satisfied if either the string matcher OR any custom matcher approves it.

### 7.6 Set utilities

Export `scope.intersect`, `scope.subtract`, `scope.normalize`, `scope.expand` (resolves implications). Used internally for PAT minting and exposed for consumer UIs.

## 8. Personal Access Tokens

### 8.1 Format

`<prefix><random>_<checksum>` — e.g., `mcp_pat_AbC...xyz_K7M9QR`.

- Prefix: configurable, default `mcp_pat_`. Lets secret scanners identify tokens.
- Random: 32 bytes from `crypto.randomBytes`, base64url-encoded (no padding).
- Checksum: CRC32 over the random portion, base32-encoded, last 6 chars.

The full token is shown to the user exactly once at mint and never persisted in any form except its SHA-256 hash.

### 8.2 Storage

SHA-256 hash + metadata (see `StoredPat` in 6.1). Never plaintext, never reversibly encrypted.

### 8.3 REST endpoints (consumer-mounted)

- `POST /` — body `{ name, scopes, expiresInDays? }`. Returns full token once.
- `GET /` — list caller's PATs (no secrets).
- `DELETE /:id` — revoke.
- `POST /:id/rotate` — mint new PAT with same scopes; old one valid for `rotationGraceSeconds` (default 0).

These endpoints require **OAuth** authentication. See 8.6.

### 8.4 Scope constraint at validation

Effective scopes on every PAT request = intersection of (scopes stamped at mint) and (current `resolveUserScopes(subject)` result). Revoking a user's permission in your domain system immediately constrains existing PATs without requiring revocation.

### 8.5 Expiry

Mandatory. Default 90 days, max 365 days. Both configurable per server.

### 8.6 PAT cannot manage PATs

A request authenticated by a PAT or static token cannot hit `/pats` endpoints — returns 403 with a clear error. Rationale: PAT compromise should not enable persistence (minting fresh siblings, rotating before revocation, etc.). Only an OAuth-authenticated user can manage PATs.

## 9. Token Validation Pipeline

Every request runs the same pipeline. First matching path wins:

1. **Bypass mode active?** Synthesize `AuthContext` from config, attach, done.
2. **Static token configured and matches?** Synthesize `AuthContext` (`tokenType: "static"`), run scope checks normally, done.
3. **Bearer token has the PAT prefix?** SHA-256, look up in store, check revocation and expiry, intersect with `resolveUserScopes`, build `AuthContext`, update `lastUsedAt` (best-effort, non-blocking).
4. **Bearer token looks like JWT?** Validate signature against cached JWKS, check `iss`, `aud == resourceIndicator`, `exp`, `nbf`. Extract `sub`, `scope`. Build `AuthContext`.
5. **Otherwise (opaque AS token)?** If `introspectionEndpoint` configured, introspect; treat the introspection response like a JWT validation result.
6. **No match:** return 401 with RFC 9728-compliant `WWW-Authenticate`.

All secret comparisons use `crypto.timingSafeEqual`. JWKS is cached with the configured TTL; cache misses fetch.

## 10. Upstream API Authentication (Token Boundary)

The framework forbids forwarding MCP tokens to upstream APIs. **v0.1 provides no built-in mechanism** for tool handlers to obtain upstream credentials; this is the consumer's responsibility.

Recommended v0.1 pattern: pre-provisioned per-user credentials stored in the consumer's own database, looked up by `auth.subject` inside the tool handler.

v0.2 will introduce a token-exchange helper based on RFC 8693 for AS implementations that support it. **Do not stub this in v0.1.** No helper, no placeholder method, no TODO comment in the public API.

## 11. Bypass Mode and Stdio

### 11.1 Bypass mode

Disables token validation. Behavior:

- Enabled via config or `MCP_AUTHKIT_BYPASS=1` env var.
- Refuses to start if `NODE_ENV === "production"` unless `bypass.allowInProduction: true`.
- Every request: synthesize `AuthContext` with `tokenType: "bypass"`, configured user and scopes.
- Emits `logger.warn` on startup naming the user and scopes.
- Emits `logger.debug` on every bypassed request.

### 11.2 Stdio transport

When using stdio via the SDK, the framework auto-enables bypass mode if no other auth is configured (no HTTP boundary to enforce on). Startup log makes this clear.

**Production stdio is not supported in v0.1.** If a consumer needs stdio in production, they configure `staticToken` explicitly.

### 11.3 Static token

A single env-var token (`staticToken` in config) treated as a synthetic PAT with fixed scopes. Goes through the normal scope-check pipeline. Suitable for CI and trusted automation. Cannot manage PATs (section 8.6).

## 12. Audit Callbacks

If `audit.onEvent` is configured, it fires for every event in `AuditEvent`. Events are awaited; an exception aborts the triggering operation (e.g., throwing from a `pat.mint` event causes the POST to 500 and the store row to roll back).

This is the integration point for SIEM, structured audit logs, anomaly detection. The framework does not persist audit events; that is the consumer's choice.

Events to emit, at minimum:

- `pat.mint` on successful POST to PAT endpoint
- `pat.use` on every successful PAT-authenticated request (rate-limit at consumer side if needed)
- `pat.revoke` on DELETE
- `pat.rotate` on rotate
- `oauth.validate` on successful JWT/introspection validation
- `oauth.reject` on any validation failure (include reason in `detail`)
- `scope.allow` / `scope.deny` per `requireScopes` check

## 13. OAuth Endpoints the Framework Owns

In Mode A, the framework owns:

- `GET /.well-known/oauth-protected-resource` (RFC 9728)
- PAT management endpoints (consumer-mounted path)
- The MCP request handler with correct 401 + `WWW-Authenticate` responses

The framework does NOT own `/authorize`, `/token`, `/device/authorization`, `/revoke`, `/introspect`. Those live on the external AS. The framework only consumes them (via JWKS fetch and optional introspection).

## 14. Security Non-Negotiables

- **Audience validation.** Every token's `aud` MUST equal the configured resource indicator. Reject missing, wrong, or array-without-match.
- **No token passthrough.** Framework never forwards MCP tokens upstream.
- **No upstream token acceptance.** Reject tokens whose `aud` doesn't match.
- **PKCE required** for any OAuth code flow the framework documents.
- **DNS rebinding protection.** Host header validation on by default; configurable allowlist.
- **Constant-time comparison** for hash and token equality.
- **PATs hashed at rest.** Never plaintext, never reversibly encrypted.
- **Refresh rotation.** Each use mints a new refresh token, old invalidated. Reuse revokes the family.
- **Short lifetimes.** Defaults: 15 min access, 30 day refresh, 90 day PAT.
- **Bypass refuses production** unless explicitly overridden, and logs loudly.
- **PAT cannot manage PATs.** Section 8.6 is enforced, not advisory.

## 15. Testing

For v0.1:

**Unit:** scope matcher (wildcards, implications, intersections), PAT format (mint, checksum, parse), JWT validation (signature, aud, exp, nbf, iss), PKCE verifier/challenge, hash comparisons.

**Integration:** in-memory end-to-end. A test fixture acts as the AS (signs JWTs with a test key, serves a fake JWKS endpoint). Coverage:

- JWT acceptance (correct signature + audience)
- PAT mint-and-use over HTTP
- PAT revoke
- PAT scope intersection when user scopes shrink between mint and use
- Refresh rotation
- Family revocation on refresh reuse
- Audit events fire for every documented case

**Security:** wrong audience, missing audience, expired token, revoked token, PAT scope escalation attempts, cross-user PAT access, refresh reuse, PKCE mismatch, disallowed Host header, PAT-managing-PAT (must 403), bypass mode in production (must refuse start), static token with insufficient scopes.

## 17. Configuration

v0.1 has **no config file format**. Consumers call `createAuthKit(config)` with a plain object. They are free to load that object from env vars, a TS file, or anywhere else.

A config file format (`mcp-authkit.config.ts`) is deferred to v0.2 alongside the CLI, which is the primary consumer of it.

## 18. Quality Bar for v0.1

Before release:

- All security non-negotiables enforced and tested
- Hello-world example runs end-to-end with the in-memory store and a test-fixture AS
- A Python script using only `requests` can: mint a PAT via the REST endpoint after OAuth auth, call the echo tool with that PAT, get expected output. First run under 5 minutes; subsequent runs under 10 seconds.
- No high or critical CVEs in the dependency tree
- Public API has zero exposed `any` types
- Quickstart doc reads cleanly to someone who's never used MCP

## 19. Build Order

1. Read the MCP authorization spec (2025-06-18) and RFCs 9728, 8414, 8707, 7636, 8628, 7662, 6750.
2. Implement the type definitions from section 6.1 in `packages/core/src/types.ts`. Get them compiling before writing any logic.
3. Token validation pipeline (section 9). Everything depends on it.
4. Scope matcher (section 7), starting with exact match, then wildcards, then implications.
5. PAT mint, format, lifecycle (section 8).
6. Memory token store implementing the full `TokenStore` interface.
7. Framework-agnostic handlers (`Handlers` from section 6.1).
8. Bypass mode and stdio auto-enable (section 11).
9. Express adapter.
10. Audit callbacks wired through every event site (section 12).
11. Hello-world example. Find rough edges; refine the API.
12. Tests (section 15).
13. Quickstart doc.

Stop at step 13. Do not implement Postgres, Hono, the CLI, a config file format, or any v0.2 feature.

When in doubt, prioritize a clean public API and explicit security defaults over breadth of features. A small framework that does auth correctly beats a big framework that does it almost correctly.
