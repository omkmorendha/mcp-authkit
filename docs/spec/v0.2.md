# mcp-authkit — v0.2 Spec

> This is the source of truth for v0.2. Issues and PRs link to anchors here
> (e.g. `docs/spec/v0.2.md#9-token-exchange-rfc-8693`). Do not edit this
> file casually — spec changes require their own PR with rationale.
>
> v0.2 builds on v0.1 ([`docs/spec/v0.1.md`](v0.1.md)). v0.1 remains the
> source of truth for everything it covered; v0.2 only adds, never replaces.
> Where v0.2 changes a v0.1 contract, the change is called out explicitly.

## 0. v0.2 Scope

v0.2 turns the v0.1 core into a production-deployable framework. The
goal is to ship every item that v0.1 §0 deferred. Nothing more.

**In scope for v0.2:**

- Durable token stores: Postgres, SQLite, Redis.
- Second web adapter: Hono.
- `mcp-authkit` CLI (init, mint-pat, verify-config, jwks-fetch, gen-secret).
- Config file format (`mcp-authkit.config.ts`) — the CLI consumes it.
- Multi-tenant authorization server (`authorizationServer` as a function).
- Dynamic Client Registration consumer (RFC 7591).
- JWT Bearer Assertion grant consumer (RFC 7523).
- Client Credentials grant consumer (RFC 6749 §4.4).
- Token-exchange helper for upstream API auth (RFC 8693).
- On-behalf-of helper (built on token exchange).
- Production stdio support (signed-handshake adapter).
- Examples: `postgres`, `filesystem`, `stdio`.
- Quickstart updates: production-deployment guide; per-store and per-adapter
  cookbooks.

**Deferred to v0.3+ (do not start, do not stub):**

- UI components for PAT management.
- gRPC adapter.
- A built-in authorization server (Mode B). v0.2 remains Mode A only.
- Cloud-vendor IAM helpers (AWS IAM, GCP Workload Identity).
- Token revocation broadcast (multi-node revocation push).
- Anomaly detection / rate-limiting middleware.
- Tracing / OpenTelemetry integration. (Audit hooks stay the single
  observability seam.)
- Migrations CLI for cross-store moves.
- Multi-region replication helpers.

Resist the urge to scaffold v0.3.

## 1. Goals

Three new problems v0.2 solves:

1. **Durability.** A production MCP server cannot lose its PAT and refresh
   state on restart. v0.2 ships Postgres and SQLite stores plus a Redis
   cache layer.
2. **Multi-framework.** Server authors do not all use Express. Hono is a
   common HTTP framework in the MCP ecosystem; v0.2 ships first-class
   support.
3. **Programmatic provisioning.** Operators need to mint a PAT or check
   config from a shell, an Ansible playbook, or a deployment script. The
   CLI plus config-file format makes the framework usable without a
   custom Node entry point.

Plus a smaller class of advanced OAuth flows (RFC 7591/7523/8693, Client
Credentials) that real production deployments consistently need and that
v0.1 punted on.

Success: a developer who shipped v0.1 in dev can swap `memoryTokenStore`
for `postgresTokenStore`, point the CLI at a config file, mint a PAT
without writing TypeScript, and run their server on Hono — without
touching the core configuration model.

## 2. Hard Constraints (Locked Decisions)

Carried forward from v0.1 unchanged: name, foundation (`@modelcontextprotocol/sdk`),
MCP spec version (2025-06-18), primary transport (Streamable HTTP),
logger (`pino`), UI (headless), JWT library (`jose`), monorepo tool
(`pnpm`), audit callbacks (always included).

New locks for v0.2:

- **CLI framework:** `commander` (locked in v0.1 §2 as the v0.2 choice).
- **SQL driver (Postgres):** `pg` (node-postgres). `Pool` is the public
  parameter — never a connection string we open ourselves. Consumers
  bring the pool; we bring the queries.
- **SQL driver (SQLite):** `better-sqlite3`. Synchronous on the hot path
  is fine; the work is bounded and short. Consumers bring the `Database`
  instance.
- **Redis client:** `ioredis`. Consumers bring the client; we run
  commands. (Used for caching, not as the source of truth.)
- **Config file loader:** `tsx` runtime for TypeScript configs;
  `c12`-style merging is NOT used — keep loading dumb and explicit.
- **Hono version:** `hono` ≥ 4.0 (Web Standards `Request`/`Response`).
- **Production stdio transport:** signed-payload handshake over stdin/stdout
  framing; see §11.

The v0.2 work MUST NOT break the v0.1 public API. `AuthKitConfig`,
`AuthContext`, `TokenStore`, `Handlers`, `RegisterToolOptions`,
`createAuthKit`, `scope.*` utilities, and the Express adapter surface
all stay source-compatible. Where v0.2 extends a type, it extends with
optional fields only.

## 3. Standards Compliance

Carried from v0.1 §4:

- MCP Authorization (2025-06-18)
- OAuth 2.1
- RFC 9728 (Protected Resource Metadata)
- RFC 8414 (AS Metadata)
- RFC 8707 (Resource Indicators)
- RFC 7636 (PKCE)
- RFC 8628 (Device Authorization)
- RFC 7662 (Introspection)
- RFC 6750 (Bearer Token)

Added in v0.2:

- **RFC 7591** — Dynamic Client Registration. Consumed against the AS;
  the framework does not implement the AS side.
- **RFC 7523** — JWT Bearer Assertion grant. The framework can request
  an access token from the AS using a signed assertion.
- **RFC 8693** — Token Exchange. Used in two places: the on-behalf-of
  helper, and the upstream-API token-exchange helper.
- **RFC 6749 §4.4** — Client Credentials grant.

Read each new RFC before implementing the corresponding feature.

## 4. Architecture Changes

v0.2 keeps the v0.1 three-layer split (Transport / Auth / Authorization)
and adds:

- **Storage layer.** `TokenStore` implementations live in their own
  packages (`store-postgres`, `store-sqlite`, `store-redis`). Each
  package exports a single factory function and re-exports nothing from
  core except the contract types. The cache adapter for Redis is a
  decorator over an underlying store — not a primary store.
- **CLI layer.** `packages/cli` produces the `mcp-authkit` binary. It is
  a thin script that loads a config file and dispatches to core APIs;
  it does NOT have its own auth logic.
- **Adapter layer extension.** `adapter-hono` joins `adapter-express`.
  Both adapters are thin sugar over the `Handlers` from §6.1 of v0.1
  and consume the same `req`/`res` style (with adaptation at the
  boundary for Hono's `Context`).
- **Upstream-credentials layer (NEW).** A helper module
  (`upstream/token-exchange`) exposes a single function for tool
  handlers to obtain an upstream credential. The function is provided
  only when the consumer opts in by configuring an AS that supports
  RFC 8693. The hard "no token passthrough" rule from v0.1 §14 is
  preserved — token exchange MINTS a new token; it does not forward.

## 5. Public API Additions

The v0.1 surface stays. v0.2 adds:

### 5.1 Multi-tenant AS

`AuthKitConfig.auth.authorizationServer` becomes:

```typescript
authorizationServer:
  | AuthorizationServerConfig
  | ((req: AuthorizationServerSelector) => Promise<AuthorizationServerConfig>)
```

The function form is called on every request that needs AS metadata
(JWKS lookup, introspection, DCR, token exchange). `AuthorizationServerSelector`
exposes the incoming `IncomingMessage` (host, headers, URL) — never the body
— plus a derived `tenantId: string | null` parsed from the host. This is
how multi-tenant servers route a request to the right AS without forking
the whole pipeline.

The static-object form remains supported. If a consumer passes a function,
the JWKS cache key includes the resolved issuer string so multiple tenants
do not collide.

### 5.2 Dynamic Client Registration (RFC 7591)

```typescript
import { registerClient } from "mcp-authkit/oauth/dcr"

const credentials = await registerClient({
  issuer: "https://auth.example.com",
  initialAccessToken: "...", // optional
  metadata: {
    client_name: "my-mcp-deployment",
    redirect_uris: [...],
    grant_types: ["authorization_code"],
    token_endpoint_auth_method: "private_key_jwt",
    jwks: {...},
    // any other RFC 7591 fields
  },
})
```

Returns the credentials returned by the AS. The framework never
persists these — the consumer decides whether to write them to disk,
secret-manager, or a database. The CLI's `init` subcommand calls this
behind a confirmation prompt.

### 5.3 JWT Bearer Assertion (RFC 7523)

```typescript
import { requestTokenWithAssertion } from "mcp-authkit/oauth/jwt-bearer"

const token = await requestTokenWithAssertion({
  issuer: "https://auth.example.com",
  audience: "https://auth.example.com/oauth/token",
  signingKey: jwkOrKeyLike,
  scopes: ["upstream:read"],
  // Optional subject (act-as-user); empty means act-as-client.
  subject: "user-123",
})
```

Returns `{ accessToken, expiresAt, scopes }`. Tokens are not cached
inside this function — the caller decides caching. (Internal usage
inside the upstream helper caches per `(audience, scopes, subject)`.)

### 5.4 Client Credentials (RFC 6749 §4.4)

```typescript
import { requestClientCredentialsToken } from "mcp-authkit/oauth/client-credentials"

const token = await requestClientCredentialsToken({
  issuer: "https://auth.example.com",
  clientId: "...",
  clientSecret: "...", // or signingKey for private_key_jwt
  scopes: ["service:read"],
  audience: "https://upstream.example.com",
})
```

Same return shape as §5.3. Audience is required and is passed as the
RFC 8707 `resource` parameter (or the AS-specific equivalent).

### 5.5 Token Exchange (RFC 8693)

```typescript
import { exchangeToken } from "mcp-authkit/oauth/token-exchange"

const upstream = await exchangeToken({
  issuer: "https://auth.example.com",
  subjectToken: "...",                 // typically auth.raw.access_token
  subjectTokenType: "urn:ietf:params:oauth:token-type:access_token",
  audience: "https://upstream.example.com",
  scopes: ["upstream:write"],
  // Optional act-as actor token; omitted for plain on-behalf-of.
  actorToken: undefined,
})
```

`exchangeToken` MUST set `resource` (RFC 8707) to the requested audience
and MUST fail-closed if the AS returns a token whose `aud` does not match.

### 5.6 Upstream credentials helper

```typescript
const upstreamFetch = authkit.upstreamFor("https://upstream.example.com")
// Inside a tool handler:
const res = await upstreamFetch({ auth, scopes: ["upstream:read"] })
// res === { token: string, expiresAt: Date }
```

Internally calls `exchangeToken` and caches the result per
`(subject, audience, scopes)` for `min(token.expiresIn, 5min) − 30s`.
The cache lives in the configured token store via two new optional
methods (see §6.2). If the store does not implement them, the helper
falls back to an in-process LRU and warns at startup.

The hard rule from v0.1 §14 ("no token passthrough") is preserved —
this helper synthesizes a new token, never the caller's.

### 5.7 CLI

```
mcp-authkit <command> [options]

Commands:
  init [path]              Scaffold a project (config, env, hello-world).
  mint-pat                 Mint a PAT against a configured store.
  verify-config            Load and validate the config file.
  jwks-fetch               Fetch JWKS for a configured issuer.
  gen-secret [length]      Generate a cryptographically strong secret.

Global options:
  --config <path>          Path to mcp-authkit.config.ts (default: ./mcp-authkit.config.ts)
  --log-level <level>      pino level (trace|debug|info|warn|error|fatal)
  --json                   Machine-readable JSON output where applicable
```

The CLI never asks for a password interactively. Secrets come from env
vars or from the config file the way the framework reads them. `mint-pat`
authenticates against the configured store using either an admin
identifier (`--user`) or the static token; it never grants itself OAuth.

Exit codes:

- `0` success
- `1` user error (bad flag, missing config)
- `2` config error (invalid file, schema violation)
- `3` runtime error (DB connect failure, AS unreachable)

### 5.8 Config file format

```typescript
// mcp-authkit.config.ts
import { defineConfig } from "mcp-authkit/config"
import { postgresTokenStore } from "mcp-authkit/stores/postgres"
import { Pool } from "pg"

export default defineConfig({
  resourceIndicator: process.env.RESOURCE_INDICATOR!,
  auth: {
    authorizationServer: {
      issuer: process.env.OAUTH_ISSUER!,
      jwksUri: process.env.OAUTH_JWKS_URI!,
    },
    tokenStore: postgresTokenStore({
      pool: new Pool({ connectionString: process.env.DATABASE_URL }),
    }),
    pat: { enabled: true, prefix: "mcp_pat_" },
  },
  scopes: { vocabulary: {} },
  resolveUserScopes: async () => [],
})
```

`defineConfig` is a typed identity function. The file is loaded via
`tsx`'s `--import` register hook so consumers do not need a transpile
step. No magic merging, no plugin system.

### 5.9 Hono adapter

Mirrors the Express adapter:

```typescript
import { honoMiddleware } from "mcp-authkit/adapters/hono"
import { Hono } from "hono"

const app = new Hono()
app.route("/", honoMiddleware(authkit, mcp))
```

Internally adapts Hono's `Context` (Web Fetch `Request`/`Response`) to
the Node-style `IncomingMessage`/`ServerResponse` that `Handlers`
expects. The adaptation layer is private and not part of the public API.

## 6. Storage Layer

### 6.1 Required `TokenStore` semantics

All v0.2 stores implement the v0.1 `TokenStore` interface as-is. They
MUST additionally:

- Provide an `init()` that is idempotent — safe to call on every
  startup. For SQL stores, `init()` runs the migrations.
- Persist `tokenHash` as raw bytes (not base64). SQL stores use `BYTEA`
  / `BLOB`. Comparisons happen in application code via
  `crypto.timingSafeEqual` after a `findPatByHash`-style index seek; no
  SQL-side hashing.
- Implement `revokeRefreshTokenFamily` as an atomic transaction.
- Implement `rotateRefreshToken` as an atomic transaction (find old by
  hash, mark `rotatedAt`, insert new) that rejects reuse — the reuse
  case revokes the entire family.

### 6.2 Optional cache methods

Two optional methods extend `TokenStore` for the upstream-credentials
helper (§5.6):

```typescript
interface TokenStore {
  // ...all v0.1 methods unchanged...

  /** Cache an upstream credential. ttlSeconds is enforced by the store. */
  cacheUpstreamCredential?(input: {
    cacheKey: string
    token: string
    expiresAt: Date
  }): Promise<void>

  /** Retrieve a cached credential, or null if missing/expired. */
  findUpstreamCredential?(cacheKey: string): Promise<{
    token: string
    expiresAt: Date
  } | null>
}
```

The memory store (v0.1) gets these added; the Postgres, SQLite, and
Redis stores ship them. Stores that omit them remain v0.1-compatible.

### 6.3 Postgres store

Package: `mcp-authkit-store-postgres`. Import: `mcp-authkit/stores/postgres`.

```typescript
postgresTokenStore({ pool: Pool, schema?: string, tableNames?: {...} })
```

- One schema, three tables: `mcp_pats`, `mcp_refresh_tokens`,
  `mcp_upstream_credentials`. Names are overridable; the schema
  defaults to `public`. The package ships SQL migrations as a numbered
  set in `migrations/` and runs them via `init()`.
- Migrations are idempotent and forward-only. Each migration is
  applied inside a transaction with `LOCK TABLE mcp_migrations IN
  EXCLUSIVE MODE` to make concurrent startups safe.
- All indexes: `mcp_pats(token_hash)` (UNIQUE),
  `mcp_pats(user_identifier)`, `mcp_refresh_tokens(token_hash)` (UNIQUE),
  `mcp_refresh_tokens(family_id)`, `mcp_upstream_credentials(cache_key, expires_at)`.
- Queries are parameterized — never string-interpolated. The framework
  rejects table-name overrides containing anything outside
  `[A-Za-z0-9_]`.
- A configured `statementTimeoutMs` (default 5000) wraps every query.
- `close()` does not close the pool — the pool belongs to the consumer.

### 6.4 SQLite store

Package: `mcp-authkit-store-sqlite`. Import: `mcp-authkit/stores/sqlite`.

```typescript
sqliteTokenStore({ database: Database, tableNames?: {...} })
```

- Single-file database. Same logical schema as Postgres; SQL dialect
  differs (`BLOB` instead of `BYTEA`, `INTEGER PRIMARY KEY`,
  `WITHOUT ROWID` where it helps).
- Migrations bundled and applied at `init()` via `journal_mode = WAL`
  and a `BEGIN IMMEDIATE` lock.
- All comparisons are constant-time in application code.
- Suitable for single-process deployments; the framework warns if
  `database.readonly` is true.

### 6.5 Redis cache decorator

Package: `mcp-authkit-store-redis`. Import: `mcp-authkit/stores/redis`.

```typescript
import { redisCache } from "mcp-authkit/stores/redis"
const store = redisCache(postgresTokenStore({...}), { client: Redis, ttlSeconds?: 60 })
```

- A decorator, not a primary store. The wrapped store is the source of
  truth; Redis caches read-mostly paths: `findPatByHash`,
  `findRefreshToken`, and `findUpstreamCredential`.
- Negative cache (a `null` result for a hash lookup) is opt-in and capped
  at 5 seconds. Default is OFF — negative caching of a non-existent PAT
  is a soft DoS vector.
- All cache values are MessagePack-encoded `Buffer`s in Redis. Keys are
  namespaced under a configurable `keyPrefix` (default `mcp:authkit:`).
- Writes (`createPat`, `revokePat`, `rotateRefreshToken`,
  `revokeRefreshTokenFamily`) invalidate the relevant cache entries
  synchronously after the underlying write succeeds.

## 7. Multi-Tenant Authorization Server

A function-form `authorizationServer` (§5.1) lets a single deployment
serve many tenants. The framework MUST:

- Cache JWKS per resolved issuer string, not per request.
- Memoize the result of the resolver for a single request lifetime to
  avoid re-resolving on every pipeline step.
- Treat a resolver throw as a 503 with a `WWW-Authenticate` of
  `error="server_error"`, NOT a 401. (The token is not the problem; the
  AS lookup failed.)
- Log resolver latency at `debug` and a histogram-friendly
  `authkit.tenant_resolve_ms` field.
- Refuse to start (config validation) if the function-form resolver
  returns an object lacking `issuer` or `jwksUri`.

The resolver runs BEFORE token parsing in the pipeline. Pipeline order
becomes: tenant-resolve → bypass → static → PAT → JWT → introspection →
401. (Order from v0.1 §9 otherwise unchanged.)

## 8. Token Exchange and Upstream Credentials

The token-exchange helper (§5.5) and the upstream-credentials helper
(§5.6) together replace the v0.1-recommended pattern of
"pre-provisioned per-user credentials in your own database." That
pattern stays valid; the new helpers add an option, not a replacement.

Hard rules:

- The subject token passed to `exchangeToken` MUST have `aud ==
  resourceIndicator`. The framework validates this before sending.
- The returned token MUST have `aud == requested audience`. If absent
  or wrong, the framework rejects and throws.
- The framework never returns the original subject token to the caller
  — only the freshly minted token. (Defense in depth against accidental
  passthrough.)
- A failed exchange does NOT fall back to the subject token. It throws.

### 8.1 On-behalf-of helper

```typescript
import { onBehalfOf } from "mcp-authkit/upstream"

const result = await onBehalfOf({
  authkit,
  auth,             // AuthContext from the tool handler
  audience: "https://upstream.example.com",
  scopes: ["upstream:read"],
})
// result === { token, expiresAt }
```

Convenience wrapper over `authkit.upstreamFor(audience)(...)`. Identical
semantics, ergonomic name.

### 8.2 Audit events for exchange

New event types added to `AuditEvent.type`:

- `upstream.exchange` — successful token exchange.
- `upstream.exchange_reject` — exchange failed (AS error, audience
  mismatch, expired subject token).

These join the v0.1 set; they are NOT a breaking change because
consumers handle `AuditEvent` as a tagged union and unknown types must
already be tolerated (TypeScript narrows; runtime ignores).

## 9. CLI Behavior Details

### 9.1 `init`

Scaffolds a directory with:

- `mcp-authkit.config.ts` (using `defineConfig`).
- `.env.example` listing required env vars.
- `server.ts` with the v0.1 hello-world content updated to load the config.
- `README.md` with run instructions.

`init` refuses to write into a non-empty directory unless `--force` is
passed.

### 9.2 `mint-pat`

```
mcp-authkit mint-pat --user <id> --name <name> --scopes <s1,s2> [--expires-in-days N]
```

Loads the config, opens the store, mints a PAT, prints the full token
once to stdout. Exits non-zero if any step fails. With `--json` the
output is `{ "token": "...", "id": "...", "expiresAt": "..." }`.

The PAT is treated as a user-owned PAT — the CLI does NOT mint
"admin" or "system" PATs. The caller must specify a real user identifier
that the operator's domain system recognizes.

### 9.3 `verify-config`

Loads the config, runs the same validation `createAuthKit` runs at
startup, prints a summary of resolved values (issuer, JWKS, audience,
scope-vocabulary keys, store type) with secrets redacted. Exits 0 if
valid, 2 if not.

### 9.4 `jwks-fetch`

Fetches the JWKS for the configured issuer (or `--issuer <url>`), prints
key IDs and algorithms, with `--json` to dump the raw JWKS. Useful for
debugging "why is my token rejected."

### 9.5 `gen-secret [length]`

Prints a `crypto.randomBytes(length).toString('base64url')`. Default
length 32. No config required.

## 10. Hono Adapter

The Hono adapter must:

- Provide a `honoMiddleware(authkit, mcp)` factory and individual
  per-route helpers (`mcp`, `metadata`, `pats`) for consumers who route
  by hand.
- Convert Hono's `Context` to `IncomingMessage`/`ServerResponse` once
  per request via a private adapter; the adapter MUST stream the
  response (not buffer) for the `mcp` handler since MCP responses can
  be large.
- Pass Hono's `c.req.raw` (Web `Request`) through where useful so the
  consumer's host-header check sees the real request.

Tests cover the same matrix as the Express adapter (v0.1 §15) plus a
streaming-response test specific to Hono.

## 11. Production Stdio Support

The v0.1 default (stdio auto-enables bypass) stays for local dev. v0.2
adds an opt-in production stdio mode:

- Triggered by `auth.stdio: { mode: "signed" }` in config.
- The framework signs every response payload with an HMAC key
  (`auth.stdio.hmacKey`) and verifies inbound signatures on every
  request. Replay is prevented by a strictly increasing per-message
  counter; a counter that does not increase is treated as a tampered
  message and the transport is torn down.
- Bypass mode is REFUSED in this mode; only the static token or PATs
  authenticate.
- Startup logs the configuration loudly (key fingerprint, not the key)
  exactly like the bypass-in-prod path.

This stays simpler than HTTP intentionally — stdio is meant for trusted
local environments. The signed-handshake mode just raises the bar over
bypass.

## 12. Security Non-Negotiables (Additions)

The v0.1 §14 list stays in force. v0.2 adds:

- **No upstream token leak.** Token-exchange helpers never log the
  minted upstream token at any level. The audit event carries token
  metadata (audience, scopes, expiresAt) but not the token itself.
- **Audience validation on exchange.** Audience-of-result MUST match
  the requested audience or the exchange fails.
- **DCR initial-access-token handling.** If supplied to `registerClient`,
  it MUST be sent over TLS and MUST NOT be persisted by the framework.
- **Client Credentials audience required.** §5.4 audience is mandatory
  for the same RFC 8707 reasons as v0.1 §14.
- **Config file load is bounded.** The config file loader times out at
  10 seconds and refuses to load any path that resolves outside the
  process CWD by default (`--config <abs-path>` is an opt-out).
- **CLI never reads secrets from argv.** `--user`, `--name`, `--scopes`
  are fine. Anything secret comes from env vars or the config file.
- **SQL queries are parameterized.** No string interpolation of user
  data. Table-name overrides validated against `[A-Za-z0-9_]`.
- **Redis values authenticated.** Cache values are checked-sum-tagged
  (HMAC over the value with a startup-derived key) so a Redis tenancy
  bug or key collision cannot serve a different store's PAT as your
  store's PAT.
- **Token exchange request size capped.** The HTTP request body to the
  AS is capped at 64 KB; longer subject tokens are rejected client-side.

## 13. Testing

For v0.2:

**Unit.** Per package:

- Postgres store: schema/migration idempotency, all `TokenStore`
  methods, transactional rotation, family revocation, upstream-cache
  methods, statement timeout behavior.
- SQLite store: same matrix as Postgres minus connection-pool
  concerns; WAL-mode behavior.
- Redis cache: hit/miss/negative-cache opt-in, write-invalidation,
  HMAC tag verification on read, key prefix isolation.
- DCR client: success path, AS error response, missing
  `client_id`/`client_secret` in response, optional initial access token.
- JWT Bearer client: assertion structure (header `alg`, `typ`,
  payload `iss`/`sub`/`aud`/`exp`/`jti`), refresh on `expires_in` < 30s.
- Client Credentials client: with and without `private_key_jwt`,
  audience required.
- Token-exchange client: audience validation of result, request body
  encoding, error mapping.
- CLI: each subcommand happy path + error cases, exit codes,
  `--json` output format.
- Config loader: TS file load, schema validation, redacted summary,
  10s timeout.
- Hono adapter: streaming response, host header, all three handlers.

**Integration.**

- End-to-end against a real Postgres in CI (Docker service): mint
  → use → rotate → revoke → family-revoke on reuse.
- End-to-end against a real SQLite in CI (no Docker; file path
  tmpfs).
- End-to-end against a real Redis in CI (Docker service) decorating
  the memory store: cache hit, write invalidation.
- Multi-tenant: two tenants configured via function-form
  `authorizationServer`, tokens minted by tenant-A's AS rejected by
  tenant-B.
- Token exchange: subject token issued by the test AS is exchanged
  for an upstream token bound to a different audience; the upstream
  token validates against the AS's upstream-mock JWKS.
- CLI: spawn the binary in a subprocess against the test fixture AS;
  `init`, `mint-pat`, `verify-config`, `jwks-fetch` all return 0.
- Hono adapter: identical handler matrix to Express, run against the
  same test fixture AS.

**Security.** Add to the v0.1 matrix:

- Token exchange that returns the wrong audience is rejected.
- DCR initial access token never appears in logs.
- SQL injection attempts via `tableNames` override are rejected.
- Redis cache value with a wrong HMAC tag is treated as a miss (and a
  warn-level log fires).
- Production stdio replay (re-played counter) tears down the
  transport.
- Multi-tenant cross-tenant token (right shape, wrong issuer) is
  rejected.
- CLI `mint-pat` with `--user` containing path-traversal characters is
  rejected.

## 15. Configuration

v0.2 introduces the config file format (§5.8) but does NOT make it
required. Calling `createAuthKit(config)` directly with a plain object
remains fully supported and is the recommended path for tests and
single-binary deployments. The config file exists for the CLI and for
operators who want a single declarative source of truth.

## 17. Build Order

1. Read RFCs 7591, 7523, 8693, 6749 §4.4. Re-read v0.1 §9, §14.
2. **Stage 1 — Storage.** Postgres store, SQLite store, Redis cache.
   Open in parallel. Each closes when its integration test passes.
3. **Stage 2 — OAuth flows.** DCR, JWT Bearer, Client Credentials,
   Token Exchange. Each is independent; build in any order.
4. **Stage 3 — Multi-tenant + upstream helper.** Multi-tenant AS
   function form first, then upstream helper (depends on Token
   Exchange from Stage 2).
5. **Stage 4 — Adapters and CLI.** Hono adapter, config-file loader,
   CLI. Config loader gates CLI; the rest is parallel.
6. **Stage 5 — Production stdio.** Independent; build alongside Stage 4.
7. **Stage 6 — Examples and docs.** Postgres example, filesystem
   example, stdio example, production deployment doc, cookbook
   entries.
8. **Stage 7 — Release.** Integration + security test matrix complete,
   changelog, version bumps, publish dry-run.

Stop at step 8. Do not implement gRPC, a built-in AS, or any v0.3 feature.

When in doubt, the v0.1 rule still applies: a small framework that does
auth correctly beats a big framework that does it almost correctly.
